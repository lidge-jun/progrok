### 메이저 상향별 breaking change 점검

메이저를 넷이나 한꺼번에 올리므로 각 릴리스가 바꾼 것을 적어 둔다. 전부 이 저장소에서는
영향이 없다고 판단했고, 판단 근거를 같이 남긴다.

| 변경 | 이 저장소 영향 |
|---|---|
| checkout v6: credential 저장 위치가 `$RUNNER_TEMP` 로 이동 | 영향 없음. 워크플로가 저장된 credential 을 재사용하지 않는다 |

| setup-node v5/v6: 자동 캐싱 동작 변경 / setup-node v7: `always-auth` 입력 제거 | 영향 없음. `package.json` 에 `packageManager` 가 없고 워크플로가 `always-auth` 를 쓰지 않는다 |

## provenance 전제조건 (npm 공식 문서 기준)

`npm publish --provenance` 는 다음을 **함께** 요구한다.

| 조건 | progrok 현황 |
|---|---|
| 워크플로에 `id-token: write` | 없음 → 이번에 추가 |
| npm CLI >= 9.5.0 | setup-node 가 가져오는 Node 20+ 번들 npm 이 충족 |
| `package.json` 의 `repository` 메타데이터 | 있음 (`https://github.com/lidge-jun/progrok.git`) |
| 공개 패키지 | `--access public` 으로 명시 |
| 지원되는 cloud CI (GitHub Actions) | 충족 |
| cloud-hosted runner (셀프호스티드 불가) | 충족 — `ubuntu-latest` |
| `--provenance` 플래그 또는 `publishConfig.provenance` | 없음 → 이번에 추가 |

`--access public` 은 엄밀히 말해 **최초 공개 시점의** 조건이다. progrok 은 이미 공개된
unscoped 패키지라 필수는 아니지만, 의도를 명시적으로 고정하는 값이라 붙여 둔다.

Trusted Publishing(npm 11.5.1+, OIDC 로 `NPM_TOKEN` 자체를 제거)은 더 나은 경로지만
npmjs 쪽 저장소 설정이 따로 필요해서 CI 파일만 고쳐서는 끝나지 않는다. 이번 범위 밖으로 두고
토큰 + `--provenance` 조합을 쓴다.

## 감사 정정 2 — 런타임 기준선과 변경 파일 (리뷰어 FAIL 반영)

리뷰어가 이 계획의 두 가지를 무너뜨렸다. 둘 다 재검증했고 둘 다 리뷰어가 맞았다.

### (1) `>=20` 은 자기 근거와 모순이다

"EOL 된 줄은 뺀다"가 근거인데 **Node 20 도 2026-04-30 에 EOL** 이다. 오늘은 2026-09-19 다.
같은 근거를 일관되게 적용하면 기준선은 `>=20` 이 아니라 `>=22` 여야 한다.

2026-09-19 기준 살아 있는 줄:

| 줄 | 상태 | 지원 종료 |
|---|---|---|
| 20 | **EOL** | 2026-04-30 |
| 22 | maintenance LTS | 2027-04-30 |
| 24 | active LTS | 2028-04 |
| 26 | current (2026-10 에 LTS 승격) | 2029-04 예정 |

따라서 **engines 는 `>=22.0.0`**, **CI 매트릭스는 `['22','24','26']`** 으로 간다.
매트릭스에서 20 을 빼는 것은 계획 확대가 아니라 같은 결정의 반대쪽이다. EOL 된 줄을
engines 에서 빼면서 CI 에서만 계속 검증하는 것은 앞뒤가 안 맞는다.

semver 영향: `package.json` 은 3.0.0 이지만 `npm view progrok version` 은 `2.0.4` 이고
`git tag` 에도 `v3.0.0` 이 없다. 3.0.0 은 아직 공개되지 않았으므로 최소 런타임 상향을
3.0.0 에 싣는 것이 semver 상 맞다. 다만 2.x 를 Node 18/20 에서 쓰던 사용자는
`engine-strict` 설정에서 설치가 **실패**하므로 3.0 릴리스 노트에 반드시 적는다.

그 "릴리스 노트"는 `CHANGELOG.md` 의 `## [3.0.0]` → `### Breaking` 절이다. 현재 거기에는
`capabilities --json` 스키마 2 와 `progrok chat` 워크스페이스 두 항목만 있고 런타임 기준선
얘기가 없다. 3.0.0 이 아직 미공개 상태라 이번 단위에서 그 절에 항목을 **추가**한다.
빠뜨리면 engine-strict 사용자가 설치 실패의 이유를 어디서도 못 찾는다.

### (2) 고칠 런타임 표기는 한 곳이 아니라 네 곳이다

앞서 "quickstart.astro 하나"라고 쓴 것은 **틀렸다**. 내 `rg` 패턴이 URL 인코딩된 뱃지를
놓쳤다. 다시 뒤져서 확인한 전체 목록:

| 위치 | 현재 | 고칠 값 |
|---|---|---|
| `package.json:38` | `">=18.0.0"` | `">=22.0.0"` |
| `package-lock.json:28-30` | `">=18.0.0"` (루트 패키지 사본) | `">=22.0.0"` |
| `README.md:6` | `node-%3E%3D18` 뱃지 | `node-%3E%3D22` |
| `site/src/pages/docs/quickstart.astro:25` | "Node 18 or newer is required." | "Node 22 or newer ..." |

`package-lock.json` 은 루트 `engines` 를 복제하므로 같이 고치지 않으면 두 파일이 어긋난다.

### (2b) EOL 제거는 CI 매트릭스만이 아니라 모든 워크플로 런타임에 적용된다

재감사에서 걸렸다. 매트릭스에서 20 을 빼면서 정작 **다른 두 워크플로가 Node 20 에 고정돼
있는 것을 그대로 뒀다**. 같은 결정이 절반만 적용된 상태다.

| 위치 | 현재 | 고칠 값 |
|---|---|---|
| `.github/workflows/pages.yml:25` | `node-version: 20` | `node-version: 22` |
| `.github/workflows/publish.yml:12` | `node-version: 20` | `node-version: 22` |
| `.github/workflows/ci.yml:28` (typecheck) | `node-version: 22` | 그대로 (이미 22) |
| `.github/workflows/ci.yml:42` (build) | `node-version: 22` | 그대로 (이미 22) |
| `.github/workflows/ci.yml:61` (매트릭스) | `['20','22','24']` | `['22','24','26']` |

publish 워크플로의 런타임은 특히 중요하다. `npm publish --provenance` 는 npm 9.5+ 를
요구하는데, EOL 런타임에 계속 묶어 두면서 provenance 를 켜는 건 앞뒤가 안 맞는다.

### (3) site 잡 추가의 비용

`pages.yml:3-7` 은 `main` 의 `site/**` push 와 수동 실행만 받고 **PR 에서는 돌지 않는다**.
그래서 PR 차단 게이트가 필요하면 `ci.yml` 에 site 잡을 넣는 게 맞다. 대신 `main` 의 site
변경에서는 CI 와 Pages 가 사이트를 **두 번 빌드**한다. 이 중복은 알고 받아들인다 — 게이트
없이 Pages 배포에서 처음 깨지는 것보다 낫다.

추가 비용이 하나 더 있다. 새 site 잡에는 `paths` 조건을 걸지 않으므로 **site 를 건드리지 않은
PR 과 main push 에서도 사이트를 빌드한다.** 잡 수준 `paths` 필터는 GitHub Actions 에 없다
— 경로 필터는 워크플로 `on.push`/`on.pull_request` 수준에만 있다. 조건부 `if` 로 흉내 내면
skip 된 잡이 pending 이 아니라 **Success** 로 보고되므로, 나중에 required check 을 걸더라도
게이트 역할을 못 한다. 사이트 빌드는 astro 한 번이라 비용이 작아서 무조건 실행을 택한다.

### (3b) 지금은 "차단" 게이트가 아니다 — advisory CI 다

3차 감사에서 걸렸다. 위에서 "PR 차단 게이트" 라고 썼지만 **이 저장소에는 브랜치 보호가 없다.**

```
gh api repos/lidge-jun/progrok/branches/main/protection  -> 404 Branch not protected
gh api repos/lidge-jun/progrok/rulesets --paginate       -> []
```

따라서 site 잡이 실패해도 지금은 merge 를 막지 못한다. `ci.yml` 의 site 잡이 만드는 것은
**PR merge 차단 게이트가 아니라 advisory CI 신호**다. 브랜치 보호/ruleset 설정은 저장소
관리 권한이 필요한 별개 작업이고 이번 범위 밖이다. 계획 본문에서 `ci.yml` 을 두고 "차단"
이라 한 표현은 이 문단이 정정한다.

(`pages.yml` 의 hidden-file 검사는 얘기가 다르다. 그건 같은 잡 안에서 업로드 앞에 있어서
브랜치 보호와 무관하게 **배포를 실제로 막는다.** (5) 절을 보라.)

그래도 잡을 넣는 이유는 그대로다. `pages.yml` 은 PR 에서 아예 돌지 않으므로, site 잡이 없으면
사이트가 깨진 것을 **main 병합 후 Pages 배포에서 처음** 알게 된다. advisory 신호라도 PR 에서
빨간불을 보는 쪽이 낫다.

| 파일 | 문제 | 수정 |
|---|---|---|
| `ci.yml` | `engines: node>=18` 선언과 매트릭스 하한 20 불일치 | ~~engines 를 >=20 으로~~ → 위 정정 2 에 따라 **engines `>=22` + 매트릭스 `22/24/26`** |

| `pages.yml:26` | `npm install` (잠금파일 무시) | `npm ci` |
| `publish.yml:14` | `npm install` | `npm ci` |
| `publish.yml` | `permissions` 없음 | `contents: read` + `id-token: write` 명시 |
| `publish.yml:16` | provenance 없음 | `npm publish --provenance --access public` |

`site/package-lock.json` 은 존재하므로 `npm ci` 로 바꿔도 잠금파일이 없어서 깨지는 일은 없다.

## engines 상향 근거

`engines` 가 선언한 하한과 CI 가 실제로 검증하는 하한이 다르다. 선언은 18, 검증은 20 이고
둘 다 EOL 이다. 살아 있는 최저 줄인 22 로 올려 **선언과 검증을 일치**시킨다.
구체적인 대상 파일 네 곳과 semver 판단은 위 "감사 정정 2" 에 있다.

## 하지 않는 것

새 CI 서비스 도입, 배포 정책 변경, npm Trusted Publishing 전환.

철회된 비대상 항목이 둘 있다. 둘 다 **구현 중에** 빠뜨릴 수 없다는 게 드러났고,
구현 검증 리뷰어가 범위 이탈로 잡아서 여기에 근거를 남기고 편입한다.

- `액션 대량 교체는 하지 않는다` — 위 "정정" 절에서 철회. `@v4` 가 현행이 아니었다.
- `캐시 전략 변경은 하지 않는다` — 아래 (4) 에서 철회.

### (4) npm 캐시: "변경"이 아니라 "누락 보충"이다

최초에 캐시를 비대상으로 둔 것은 `ci.yml` 만 보고 "이미 캐시가 있다"고 판단했기 때문이다.
실제로는 **`pages.yml` 과 `publish.yml` 에는 캐시가 아예 없었다.** 기존 전략을 바꾸는 게
아니라 같은 전략을 적용받지 못한 두 워크플로에 마저 적용하는 일이다. `npm install` 을
`npm ci` 로 바꾸면서 캐시 없이 두면 매 실행이 전체 레지스트리 왕복이 된다.

| 위치 | 캐시 | 대상 lockfile |
|---|---|---|
| `ci.yml` typecheck/build/test | 이미 있었음 | 루트 (기본값) |
| `ci.yml` site (신설) | 추가 | `site/package-lock.json` (`cache-dependency-path`) |
| `pages.yml` | 추가 | `site/package-lock.json` |
| `publish.yml` | 추가 | 루트 (기본값) |

site 캐시가 루트 캐시와 충돌하지 않는지 확인했다. `setup-node@v7` 은 지정된
`cache-dependency-path` 를 직접 해시해 캐시 키를 만들고, 두 lockfile 의 SHA-256 이
실제로 다르므로 키가 갈린다. (검증 리뷰어가 두 해시를 직접 비교해 확인)

### (5) hidden-file 검사: 일회성 확인에서 영구 게이트로 승격

원래는 "이번에 `find site/dist -name '.*'` 가 비었는지 본다" 는 일회성 검증이었다.
구현에서는 `ci.yml` site 잡의 **영구 실패 스텝**으로 넣었다. 승격한 이유:

`upload-pages-artifact@v5` 의 `include-hidden-files` 기본값은 `false` 다 (공식
`action.yml` 로 확인). 즉 산출물에 hidden file 이 생기면 **에러 없이 조용히 빠진 채**
배포된다. 일회성으로 오늘 0개인 걸 확인해 봐야, 내일 astro 설정이 바뀌어 `.well-known/`
같은 게 생기면 아무도 모른다. 조용한 실패는 게이트로 막는 게 맞다.

검사를 **두 워크플로에 모두** 넣는다. 재검증 리뷰어가 `ci.yml` 에만 넣은 초안을
잡아냈다 — `ci.yml` 은 브랜치 보호가 없어 advisory 이고, 실제 업로드는 `pages.yml` 이
따로 한다. `ci.yml` 에만 있으면 CI 가 빨간불이어도 Pages 는 그대로 누락된 사이트를
배포한다. 그래서:

| 위치 | 역할 |
|---|---|
| `ci.yml` site 잡 | PR 에서 빨리 알려주는 advisory 신호 |
| `pages.yml`, `upload-pages-artifact` **직전** | 실제 배포 게이트 |

배포를 막는 것은 `pages.yml` 쪽이다. 같은 잡 안에서 실패하므로 브랜치 보호와 무관하게
업로드가 일어나지 않는다.

비용은 `find` 한 번이다.

## 검증

- 워크플로 YAML 문법 유효성. 쓰는 파서를 기록에 남긴다:
  `node -e 'const{readFileSync}=require("fs");...'` 대신 저장소에 이미 있는 의존성으로
  파싱한다. yaml 파서가 없으면 `python3 -c "import yaml,sys;yaml.safe_load(...)"` 를 쓰고
  어느 쪽을 썼는지 체크 문서에 적는다.
- `npm ci`가 로컬에서 성공하는지 (잠금파일 정합성)
- engines 상향 후 `npm run build`, 테스트 통과
- `node --version` 이 22 미만인 환경은 로컬에 없으므로 engines 는 선언 정합성만 확인한다
- `npm --prefix site ci && npm --prefix site run build` 가 성공하는지 (리뷰어가 임시 복사본에서
  성공과 45페이지 생성을 확인했으나, 이 체크아웃에서 직접 재확인한다)
- 사이트 빌드 직후 `find site/dist -mindepth 1 -name '.*'` 가 **빈 결과**인지.
  `upload-pages-artifact` v4+ 가 hidden file 을 기본 제외하므로, 산출물에 hidden file 이
  생기면 조용히 빠진다. `site/dist` 는 `.gitignore` 대상이라 커밋으로는 확인할 수 없고
  빌드 후 직접 봐야 한다.

### 검증 명령 (3차 감사에서 두 개가 깨져 있어 교체)

앞서 적었던 두 명령은 실제로 돌려 보니 못 쓴다.

`rg -n "node-version" .github/workflows` 는 **false-green** 이다. `ci.yml:61` 의 매트릭스는
`node: ['20','22','24']` 라 `node-version` 이라는 문자열이 없어서 안 잡힌다. Node 20 이
매트릭스에 남아 있어도 통과해 버린다.

`rg -n "18|%3E%3D18" ...` 는 **false-red** 다. 실제로 돌리면 102줄이 걸린다. 포트 번호
`127.0.0.1:18645`, `ws@8.18.3`, 그리고 `package-lock.json:2152`·`:2561` 의 **전이 의존성**
`"node": ">=18.0.0"` 까지 잡는다. 전이 의존성 쪽은 우리가 고칠 대상이 **아니다** — 건드리면
잠금파일이 상류와 어긋난다. 고칠 것은 `packages[""]` 의 루트 engines 하나뿐이다.

쓸 수 있는 명령은 이것들이다.

```sh
# Node 20 고정이 워크플로에 남았는지 (매트릭스 값까지 포함)
rg -n "\\b20\\b" .github/workflows

# 런타임 하한 선언 두 곳이 일치하는지 (전이 의존성을 건드리지 않고 루트만)
node -e 'const p=require("./package.json"),l=require("./package-lock.json");
  console.log(p.engines.node, l.packages[""].engines.node)'

# 사용자 대면 표기 두 곳
rg -n "%3E%3D" README.md
rg -n "Node [0-9]+ or newer" site/src
```

### 이번 단위가 증명할 수 없는 것 (별도 acceptance gate)

액션 메이저 4개 상향과 provenance 는 **로컬에서 증명이 끝나지 않는다.** 로컬 검증은 YAML
파싱과 빌드 성공까지이고, 액션이 호스티드 러너에서 실제로 도는지는 GitHub 에서만 알 수 있다.
정직하게 분리해 둔다.

| 항목 | 증명 시점 | 증거 |
|---|---|---|
| 액션 v7/v5 가 실제로 도는지 | push 후 첫 CI 실행 | Actions 실행 로그 |
| Pages 빌드/배포가 새 액션으로 되는지 | `workflow_dispatch` 수동 실행 | Pages 배포 결과 |
| `npm publish --provenance` 가 통과하는지 | **다음 `v*` 태그 릴리스 시점** | npm 패키지의 provenance 배지 |

publish 워크플로는 태그 push 로만 돌기 때문에 이번 단위에서 실행 증거를 만들 수 없다.
"고쳤다"가 아니라 "고쳤고 다음 릴리스에서 확인한다"로 적는다.
